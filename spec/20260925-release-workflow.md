# Automated release workflow

## Goal

A GitHub Actions workflow that, on every push to `master`, produces a downloadable release of the macOS app with no manual steps:

1. Bump the app's marketing version (patch component).
2. Build the app in Release configuration.
3. Package the built app into a DMG.
4. Publish a GitHub Release with the DMG attached.

## Signing

Whether team `4L8444Q855` (`DEVELOPMENT_TEAM` in the project) is enrolled in the paid Apple Developer Program is unconfirmed. A paid membership is required for a `Developer ID Application` certificate, which in turn is required for notarization. Without either, a DMG built by this workflow cannot open with a plain double-click on another Mac — Gatekeeper blocks it as "damaged" until the user manually clears the quarantine attribute.

Given that, this workflow builds with **ad-hoc code signing** (`CODE_SIGN_IDENTITY="-"`, no team, no provisioning profile): no paid account or secrets are required, and the app's entitlements (`LookinClient/Lookin.entitlements`) still get embedded, unlike a fully unsigned build. It is not notarized.

Release notes generated by the workflow include the install workaround (clear quarantine via `xattr`), matching the pattern below:

```
## 安装

下载 `Supa Lookin-X.Y.Z.dmg`,打开后将 `Supa Lookin.app` 拖入"应用程序"文件夹。

如果 macOS 显示 **"Supa Lookin.app" is damaged and can't be opened. You should move it to the Trash.**,请确认安装包来自此 Release,然后在"终端"执行:

    xattr -dr com.apple.quarantine "/Applications/Supa Lookin.app"

完成后再次打开 `Supa Lookin.app`。
```

**Follow-up (out of scope for this spec):** once paid Apple Developer Program membership on team `4L8444Q855` is confirmed, a later spec should add a `Developer ID Application` certificate and notarization credentials as GitHub Secrets, switch the build to Developer ID signing, add a notarize + staple step, and drop the quarantine workaround from the release notes.

## Version bump

- Trigger: `push` to `master` — every push bumps the version, with no manual dispatch step.
- Only the patch component of `MARKETING_VERSION` is incremented (e.g. `1.0.7` → `1.0.8`).
- Only the `SupaLookin` app target's `MARKETING_VERSION` (the configuration blocks that also set `PRODUCT_BUNDLE_IDENTIFIER = icu.retrouvailles.supalookin`) is touched. The project-level default build settings also carry a `MARKETING_VERSION` (currently `1.0.0`, unused by the shipping target) and are left alone.
- `CURRENT_PROJECT_VERSION` (build number) is **not** touched by this workflow.
- The bump is committed straight to `master` by the workflow (author `github-actions[bot]`), then tagged `vX.Y.Z`. Both the commit and the tag are pushed using the workflow's default `GITHUB_TOKEN`; GitHub does not re-trigger workflow runs for pushes made with that token, so this does not loop.

## Build

- `pod install` (Pods/ is gitignored, so CI resolves it fresh via CocoaPods).
- `xcodebuild -workspace SupaLookin.xcworkspace -scheme SupaLookin -configuration Release build`, with `CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM=` overrides for ad-hoc signing as described above.
- Runner: `macos-14` (matches the project's macOS 14.0 deployment target).

## DMG packaging

Built with `hdiutil` (no extra tooling to install): stage `Supa Lookin.app` plus an `Applications` symlink in a folder, then `hdiutil create -format UDZO`. Filename: `Supa Lookin-X.Y.Z.dmg`.

## GitHub Release

- Tag and title: `vX.Y.Z`.
- Body: the install-instructions template above, with the actual version/filename substituted in.
- Asset: the DMG.
- Created via `gh release create` using the workflow's `GITHUB_TOKEN` (workflow permission `contents: write`).

## Update: ad-hoc build failed to launch (found after first release)

The first DMG built by this workflow installed but would not launch: `dyld[...]: Library not loaded: @rpath/LookinShared.framework/... code signature ... not valid for use in process: mapping process and mapped file (non-platform) have different Team IDs`.

Root cause: `ENABLE_HARDENED_RUNTIME = YES` is set on the app target, and Hardened Runtime enforces Library Validation by default — it rejects loading embedded frameworks whose ad-hoc signature isn't provably from the same source as the main executable's, even when both are ad-hoc (no team). This is independent of the Developer ID/notarization gap already described above; it reproduces with any ad-hoc-signed, hardened-runtime build, including ones made straight from Xcode locally.

Fix: added `com.apple.security.cs.disable-library-validation` to `LookinClient/Lookin.entitlements`, alongside the existing `com.apple.security.cs.debugger` entry. Verified locally — rebuilding with the workflow's exact `CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM=` settings and launching the resulting binary now starts up cleanly. No workflow changes were needed; the entitlements file is picked up automatically since `CODE_SIGN_ENTITLEMENTS` already points to it.

## Update: CocoaPods removed (see `20261025-spm-migration.md`)

All dependencies now come from Swift Package Manager: local packages under `Packages/`, plus Sparkle from its remote repository, pinned in the committed `Package.resolved`. The workflow no longer runs `pod install`, and builds with `xcodebuild -project SupaLookin.xcodeproj` instead of `-workspace SupaLookin.xcworkspace`; `xcodebuild` resolves the packages itself. The ad-hoc signing overrides are unchanged, and so is the `disable-library-validation` entitlement, since Sparkle is still an embedded dynamic framework.
